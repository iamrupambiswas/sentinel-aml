Authentication & roles (Keycloak JWT)

How a caller gets a token, how the gateway and every service check it, and which role may call which endpoint (Phase 6, ADR-006).

Step by step

  1. A person (password grant, client sentinel-postman) or the core-banking feed (client credentials, client sentinel-ingest) asks Keycloak for a token.
  2. Keycloak signs a JWT whose realm_access.roles lists every effective role. Composite roles expand the hierarchy: ADMIN includes SENIOR_ANALYST, ANALYST and INGEST.
  3. The gateway's SecurityConfig checks the token (signature with Keycloak's cached public keys, exp, iss). Missing or invalid = 401. It does not check roles.
  4. The request goes to the owning service with the Authorization header unchanged.
  5. The service's shared SentinelSecurityConfig validates the token again (so calling a service port directly also needs a token), then keycloakJwtConverter() turns each realm role into ROLE_<role> and uses preferred_username as the principal name.
  6. The service's own SecurityRoutes bean decides by method and path. Anything without a rule is denied (403), even for ADMIN.
  7. Controllers that record who did something (rule updates) take the name from Principal, never from the request body.
