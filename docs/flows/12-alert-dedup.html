Alert de-duplication & analyst workflow

How rule hits from detection become ONE alert per account, rule and time window, safely under concurrent consumers and redelivery, and how analysts move an alert through review.

Steps 1-5 run in one MySQL transaction per event. Any exception rolls back the JMS session too, so the broker redelivers.

Step by step

  1. DetectionHitsConsumer.onHits() receives a RuleHitsDetectedEvent (one per account per transaction, 1+ rule hits).
  2. AlertIngestService.ingest() sorts the hits by de-dup key accountId:ruleCode:windowBucket, so two events touching the same alerts lock them in the same order.
  3. INSERT ... ON DUPLICATE KEY UPDATE creates the alert or does nothing. With useAffectedRows=true it returns 1 = created, 0 = existed.
  4. SELECT id ... FOR UPDATE takes the alert's exclusive row lock up front: concurrent hits for one alert queue instead of deadlocking.
  5. Under that lock, if (event_id, rule_code) is already in alert_hit the event is a redelivery and is skipped. Otherwise the hit is attached with a plain INSERT.
  6. One UPDATE moves the counters atomically: hit_count + 1, risk_score = GREATEST(...), latest explanation, first/last transaction time.
  7. Analysts list alerts (highest risk first), open one with all hits, and move it through the workflow. @DynamicUpdate + @Version mean a status change never overwrites a hit count the consumer added meanwhile.

Any other move returns 409. New hits on a closed alert in the same window are still attached (hit_count grows) but do not reopen it.
