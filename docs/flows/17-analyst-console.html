Step by step

  1. Sign-in. middleware.ts sends a request without a session to /login. The button starts next-auth's Keycloak sign-in: authorization code with PKCE S256 and state. Keycloak redirects back to /api/auth/callback/keycloak; next-auth swaps the code (plus verifier and client secret) for tokens.
  2. Session cookie. lib/auth.ts keeps only access token, refresh token, expiry, username and roles in next-auth's encrypted, httpOnly cookie (about 2.9 KB). The browser never sees a token.
  3. Refresh. On every page and /api/live request, middleware.ts checks the expiry. Within 30 s of it, refreshSession() posts the refresh token to Keycloak and rewrites the cookie on the response and on the current request. A refused refresh means the Keycloak session ended: cookie cleared, back to /login.
  4. Data. Server components call api() in lib/api.ts, which sends Authorization: Bearer <the user's token> to the gateway. Changes (status, rule edit, replay, delete) are server actions doing the same. The services' own role rules decide; the UI only hides what a role can't do.
  5. Live changes. AlertIngestService (new or merged hit) and AlertQueryService.changeStatus raise an AlertChangedEvent inside their transaction. AlertChangePublisher sends it to the topic only after commit.
  6. Fan-out. Every alert-case pod's AlertStreamService listens on the topic (pub/sub factory) and writes the event to each of its open SseEmitters. A comment line every 25 s keeps idle connections open. A failed send drops that connection only.
  7. Browser. LiveAlerts opens EventSource('/api/live'). That route handler opens the gateway stream with the user's token and pipes it through. On each alert event it shows a notice (link to the alert) and calls router.refresh() after 500 ms without further events.
  8. Sign-out. next-auth clears the cookie, then redirects to Keycloak's logout endpoint with client_id and post_logout_redirect_uri; Keycloak asks for confirmation (no ID token is stored) and returns to /login.
