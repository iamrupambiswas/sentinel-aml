Poison messages & dead-letter replay

What happens to a message a consumer can never process, how the broker stops retrying it, and how an operator inspects, replays or deletes it.

Policy 5 attempts, 1 s x2 backoff, max 30 sDLQs DLQ.<queue>API /api/v1/ops/dlq

Policy lives in infra/artemis/broker.properties, mounted into the broker container.

Step by step

  1. A listener throws (bad JSON, DB down, a bug). Because the session is transacted (spring.jms.listener.session.transacted=true) the message goes back to the broker.
  2. The broker redelivers after 1, 2, 4 and 8 s (redeliveryDelay 1000, multiplier 2, max 30 s). Short outages heal on their own.
  3. After the 5th failure the broker moves the message to queue DLQ.<source> on address DLQ, auto-created on first use, and stamps _AMQ_ORIG_QUEUE.
  4. GET /api/v1/ops/dlq shows the depth of each DLQ; GET /api/v1/ops/dlq/{queue} browses messages without consuming them.
  5. After fixing the cause, POST /{queue}/replay[?messageId=] moves messages back. Receive and send share one transacted session, so a crash can neither lose nor duplicate a message. Broker-internal properties are dropped, so attempts restart at 1.
  6. A message that can never succeed is removed with DELETE /{queue}/messages/{messageId}.
  7. Local demo: POST /{queue}/poison-test sends an unreadable message (enabled by sentinel.ops.poison-test-enabled, local only).

Gotchas handled

GotchaHandling
Artemis default is redeliver immediately, foreverPolicy above: bounded attempts + backoff
DLQ queue does not exist until the first dead letterTreated as empty (depth 0), not an error
Spring's CachingConnectionFactory keeps consumers open; they can hold prefetched DLQ messagesDeadLetterService unwraps it and uses a fresh connection per call
Browsing does not count as delivery, so delivery count reads 0Not shown; being in a DLQ already means 5 attempts were used
The API must not read arbitrary queuesAllow-list: only sentinel.txn.ingested and sentinel.detection.hits (400 otherwise)
