Step by step

  1. An action happens, e.g. a senior reveals a national ID. The service calls AuditPublisher.record(action, entityType, entityId, details); the actor is the JWT username (CurrentUser).
  2. After commit, the event goes to the sentinel.audit.events queue. If the action rolls back, nothing is sent. alert-case's own events skip the queue and are appended in the same transaction.
  3. AuditEventConsumer calls AuditLog.append(), which locks the single audit_chain_head row, ignores an event_id it already has, computes SHA-256(seq | fields | prev_hash) (AuditChain.hash), inserts the row and moves the head. The lock is released at commit.
  4. Failures roll back the JMS session: the broker retries, then parks the event in DLQ.sentinel.audit.events (shown on the Dead letters page, replayable without duplicates).
  5. GET /api/v1/audit/verify (ADMIN) walks the chain from entry 1, recomputes every hash and compares links and the head. It names the first changed or missing entry.
  6. Cases: CaseService locks the case row, enforces expectedVersion, the status rules, SENIOR_ANALYST + resolution for closing, and one case per alert (UNIQUE(alert_id)). Each change writes its audit entry in the same transaction; the case page shows them as History.
  7. PII: customer responses always carry idNumberMasked. POST /api/v1/customers/{id}/national-id/reveal {reason} (SENIOR_ANALYST) returns the full value and records PII_REVEALED. LoggingAspect.redact() masks idNumber, tokens and secrets in request logs.
