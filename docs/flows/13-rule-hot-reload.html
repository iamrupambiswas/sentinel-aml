Live rule tuning & hot reload

How a compliance officer changes a rule threshold through the API and every detection pod evaluates with the new value within milliseconds, with an audit trail and no lost updates.

Service detection-serviceTopic sentinel.rules.changedMeasured 45 ms commit-to-live

    U->>API: PUT /api/v1/rules/CTR_THRESHOLD {thresholdAmount, expectedVersion, changedBy, reason}
    API->>S: update(code, request)
    S->>DB: load aml_rule, check expectedVersion (409 if stale)
    S->>DB: UPDATE aml_rule WHERE version = old (JPA @Version bumps it)
    S->>DB: INSERT aml_rule_version (snapshot, who, why)
    S-->>API: 200 saved as version N
    Note over S,DB: COMMIT
    DB-->>P: @TransactionalEventListener(AFTER_COMMIT)
    P->>T: RulesChangedEvent(code, N, changedBy, changedAt)
    T-->>L: one copy per subscribed pod
    L->>C: refreshRuleCache() (atomic Map swap)
    L->>L: log + metric commit-to-live lag

Step by step

  1. RuleAdminController validates the body (@Valid: weight 0-100, non-negative numbers, reason and changedBy required).
  2. RuleAdminService.update() rejects a stale expectedVersion with 409, and unknown param names with 400 (each rule declares supportedParams()).
  3. Changed fields are applied; saveAndFlush bumps the JPA @Version. A concurrent commit in between also gives 409.
  4. A full snapshot is inserted into aml_rule_version, then an in-process RuleChangedApplicationEvent is raised.
  5. RuleChangePublisher runs only AFTER COMMIT and sends RulesChangedEvent to the TOPIC with the dedicated topicJmsTemplate.
  6. Every detection pod's RulesChangedListener (topic factory, pub/sub) reloads the cache and records sentinel_rule_reload_lag.
  7. GET /api/v1/rules shows version (DB) next to loadedVersion (this pod) to prove the change is live.
